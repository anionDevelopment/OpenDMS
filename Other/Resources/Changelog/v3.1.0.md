# Release notes

## Changes

- Added OIDC-login-functionality.
- many functional changes
- Fixed a database-migration failure on MariaDB caused by an invalid SQL comment (missing whitespace after `--`) in the storage-location custom metadata-fields migration.
- the fonts "Roboto" and "Material Icons" are delivered with the application instead of being loaded from an external font-service, so the user-interface does not depend on the availability of that service and no request leaves to it
- added visual-regression-tests for the document-list and for the page of a single document
- the user-menu is now at the same position in every browser. It was located 20 pixels higher in firefox than in chromium and in webkit, because the gap between its title and its first entry was a line-break inside a flex-container, and a line-break is a flex-item which the engines give a different height. The gap is a margin now
- the preview of a document is now the same height in every browser. On the page of a document it was 79 pixels high in chromium and in firefox but 107 pixels high in webkit, which moved everything below it; the reason was that the element was an inline-element which contains a block-element
- the visual-regression-tests additionally check that all browsers lay every checked page out the same way, which the comparison of a screenshot with the baseline of its own browser can not detect
- the color-scheme of the user-interface (system, light or dark) can be chosen in the header of every page and is stored per user in the new table "UserSettings", so the choice is applied again after a new login and on another device. A user who never chose anything keeps "system", which follows the setting of the operating-system of that user
- the user-interface follows material 3 completely now. The colors come from a palette which is generated from two seed-colors ("Other/../src/styles/_theme-colors.scss"), and every color-token exists in a light and in a dark value, which the css-property "color-scheme" selects. There is therefore no second theme which would have to be kept in sync with the first one, and the few places which had a fixed color (a popup with a white background, a grey hint-text, the area behind a preview) use the tokens of the theme now and are readable in both schemes
- the visual-regression-tests check the user-settings-page in the light and in the dark color-scheme. The dark scheme is not a variation of a few colors of the light one, so a regression which only occurs there - an element which keeps a bright background, for example - would stay unnoticed if only one of the two was checked
- Removed the configuration of GitVersion, which is not used anymore
- Updated the GRYLibrary-dependency to version 2.0.31
- The backend and its tests now declare their runtime-identifiers (win-x64, linux-x64, linux-arm64) directly in their csproj-files instead of passing them as a build-argument, which simplifies the build-script
- Fixed test-cases that referenced the ambiguous name `TestKind` by fully qualifying it as `GRYLibrary.Core.Misc.TestKind`, and added the missing `TestKind`-attribute to four test-cases in `OpenDMSBackendControllerTests`
- Added a `FastLane`-option to the build-pipeline to allow a faster build-run, and updated the pinned SCBuilder-image-version
- Removed the pinned skill-version from the automation- and common-project-structure-skills and documented that running `scbuildcodeunits` in parallel on multiple repositories might cause errors
- the user-settings-page contains a culture-selector (the component "@aniondev/ngx-culture-selector") which lets the user choose between English, German and Spanish. The offered cultures are a fixed list for now and the chosen culture is not applied to the application yet, because the selector is only tried out at the moment
- Fixed the unit-test of the document-list-page, which failed because its mock of the storage-service did not provide the method "hasAccessToken" which the theme-service calls
- the unit-tests of the frontend are executed by Vitest instead of by Karma and Jasmine, because Karma is not the test-runner the Angular-team develops against anymore. The tests now run in "jsdom", so no browser has to be installed on the build-host anymore. The test-coverage is still written as a cobertura-file with the same structure as before, because the coverage-provider "istanbul" uses the same library to write it which Karma used. The testcases keep being compiled just-in-time, which is what karma did as well: the new build-configuration "Test" sets "aot" to false, because with ahead-of-time-compilation the bundler drops the module-scopes from the bundle and TestBed can then not resolve the components an imported NgModule exports.
- a document can now be indexed with tags and with metadata, which the GOBD requires so that documents stay findable and machine-evaluable (issue 14). A tag is a named and colored label which exists installation-wide and can be assigned to arbitrarily many documents; the custom metadata-fields of a storage-location hold the values of a document, for example its document-type or its contact/sender. Both are changed on the page of a document in the web-UI, and every change is audit-logged like every other change-operation. The retention-date stays where it already was ("DeleteIsNotAllowedBefore" and "MustBeHardDeletedAfter"), so that there is exactly one place which decides when a document may and must be deleted, and searching over tags and metadata remains issue 15
- the tag-functionality was only half-present before and is complete now: the api offers creating a tag, assigning it to a document and removing the assignment again (none of the three was reachable over the api), and "DatabasePersistence.UnassignTag" was not implemented at all and threw a "NotImplementedException". A tag-name must not be empty and must not be used twice, and assigning an already-assigned tag (or removing a not-assigned one) is rejected instead of being ignored silently
- "Tag" compares itself by its id now, like every other business-type does. Without that, two instances of the same tag which were loaded separately from the database counted as different tags, so the set of tags of a document could contain the same tag more than once
- the backend references GRYLibrary as the published package (version 2.1.0) again instead of referencing the project-file of a working-copy next to this repository. The project-reference made the build depend on a folder outside of the repository, and because that project declares only the runtime "win-x64" the build for "linux-x64" and "linux-arm64" could not work at all. The package brings no transitive dependencies with it, so the dependency "System.IdentityModel.Tokens.Jwt" which its OIDC-functionality needs is declared here explicitly, like the other dependencies of the library already are
- the message-extraction of the frontend works again. It extracted 0 messages and thereby emptied every translation-file on every run of "CommonTasks.py" (and therefore of the build), because the target "extract-i18n" had no build-target and used a default one which does not exist in this codeunit. This is the same kind of defect which was found for the test-target before. It uses the builder "@angular/build:extract-i18n" with the build-target "OpenDMSFrontend:build:Development" now and extracts 97 messages
- the localized build works again. Three translation-units ("hello_user", "content_view_document_count" and "users") still carried the source-text of an earlier version in every language-file, and for two of them that old source contained an INTERPOLATION-placeholder which the current message does not have, which the localized build rejects. The source-texts are the extracted ones now; no translation was changed
- the size-budget of the web-application was raised from 500kB/1MB to 1.5MB/2MB. The application has an initial raw size of 1.35MB (251kB transferred), so the previous value was the never-adjusted default of a new Angular-project and made the localized build fail. The failure only became visible now, because the localized build did not get that far while the message-extraction was broken
- the migration to the build-system "@angular/build" is complete: the serve-target was the last one which still used the webpack-based builder "@angular-devkit/build-angular", which is not a dependency anymore. That package was the reason why the dependency-tree of the web-application was inconsistent ("npm ls" reported "chokidar", "semver" and "@noble/hashes" as invalid and failed, which made the generation of the bill-of-materials fail): it pulls a webpack-dev-server whose transitive "@noble/hashes" and "chokidar" contradict the versions which the test-environment "jsdom" and the current "@angular-devkit/core" need. The option "--disable-host-check" of the start-script, which only the old builder knows, became "--allowed-hosts=true", which has the same effect
- the secret-scan of the build no longer stops at the development-certificate inside the built oci-image. That certificate is already recorded as a known false positive in ".betterleaks.toml", but only under the path it has in the repository, while the dockerfile copies it to "/Workspace/Other/Certificates" in the image; that path is part of the same allowlist-entry now. What stays open and belongs into an own issue: there is only one image, so a productively used image carries the private key of the development-certificate as well
- feature 14 ("tagging and indexing with metadata") is complete now. A tag can be renamed, be given another color and be deleted (deleting it removes it from every document it is assigned to), and a tag is either a global tag, which every user can use and which only an administrator can create, change and delete, or it belongs to a single user, who is the only one who can see, use, change and delete it. The tags are managed on the settings-page of the web-UI
- a custom metadata-field can be of the type "double" or "timestamp" as well, not only of "string" or "bool" (issue 2). A value is validated against the type of its field and is stored in a normalized representation (a number in the invariant culture, a timestamp as an iso-8601-timestamp), so that every reader gets the same format back regardless of the culture of the writer
- a custom metadata-field can be renamed. Its type stays unchangeable on purpose, because the values which the documents already hold for it were validated against it
- moving a document into another storage-location transfers the values it holds to the fields of the new storage-location which have the same name and the same type; a value which has no such field is removed. Before, such a value stayed in the database where it was neither shown nor changeable any more but reappeared when the document was moved back. Both cases are audit-logged
- the search finds a document by the values it holds for the metadata-fields of its storage-location as well, not only by its title, its filenames, its ocr-content and its tags (part of issue 15)
- the retention-dates of a document ("DeleteIsNotAllowedBefore" and "MustBeHardDeletedAfter") can be set via the api and on the page of the document (issue 9), and the deletion-lock is enforced technically: a hard-deletion is refused as long as the retention-period of an affected document has not ended, for every caller including the automatic housekeeping (issue 10)
- the health-check-endpoint works in a test-run again. The health-check needs the initialization-service, which was only registered when the execution-mode is "RunProgram", so in a test-run the server either did not start at all (in an environment which validates the services while the application is built) or answered every request to the health-check with an error. The distinction is between the analysis-mode, which only inspects the routes to generate the api-specification, and every other execution-mode now, so a test-run gets the same fully functional server as a normal run
- the test-coverage of the backend is collected again when an integration-test which starts the server runs. The test-framework let the thread of the server keep running after the testcase had finished, but the test-runner reads the collected coverage directly after the last testcase while the process writes it when it ends, so the coverage of the whole testrun was reported as 0%. The test-framework waits for the thread of the server when it stops the server now, and an error of the server is reported by the testcase instead of terminating the test-process. The testcase "HealthCheckIsWorking", which was deactivated because of that, runs again
- the condition which decides whether the custom metadata-fields are shown was moved from the template of the content-view into its component. The html-formatter which the linting runs breaks a template which contains the operator "&&" (it splits it into two lines), which made the application not compile anymore after every run of the linting; the last commit of the repository had to repair exactly that. No template contains that operator anymore
